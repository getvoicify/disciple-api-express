Deployment Readiness

⚠️ Pre-Deployment Requirements

  • Redis URL: Required in production for BullMQ queue
  • Keycloak Configuration: IAM_ENDPOINT, IAM_REALM, KEYCLOAK_CLIENT_ID, KEYCLOAK_CLIENT_SECRET
  • Database: PostgreSQL with existing schema (no migrations needed)
  • Worker Deployment: Separate container/process from API server

Environment Variables Required

IAM_REALM=your-realm
KEYCLOAK_CLIENT_ID=your-client-id
KEYCLOAK_CLIENT_SECRET=your-client-secret

# Environment
NODE_ENV=production

Deployment Steps

  1. Run Migration Script: Execute npm run migrate:church-memberships to sync existing data
    • Supports --dry-run flag for preview
    • Safe to run multiple times (idempotent)
    • Recommend running during low-traffic window
  2. Deploy API Server: Standard deployment with updated endpoints
  3. Deploy Worker: Separate deployment using src/worker.ts
    • Concurrency: 1 (to avoid overwhelming Keycloak API)
    • Graceful shutdown handlers for SIGTERM/SIGINT
    • Monitors BullMQ queue for church membership events
  4. Monitor Logs: Watch for event emission and processing logs
  5. Execute Manual Verification: Follow guide in implementations/7-manual-verification-guide.md

Success Metrics (from spec)

  • All church membership changes reflected in Keycloak within 30 seconds
  • Zero data loss during Keycloak API outages (outbox guarantees delivery)
  • Dead letter queue captures <1% of sync jobs

Known Limitations

  • No Ownership Transfer Endpoint: Infrastructure is ready, but no endpoint exists for transferring church ownership. When this endpoint is added, it can easily integrate with existing event emission pattern.
  • Development Mode: Without Redis URL configured, event emission is disabled with warning logs. This is intentional for local development.
  • Worker Concurrency: Set to 1 to avoid overwhelming Keycloak API. May need adjustment based on production load.
